# T41：渲染层门面收敛——「点击发送只调一个函数」（讨论稿，未定稿）

> 起因（2026-09-21 用户讨论）：「比如我点击发送按钮，我只要调用封装好的发送按钮就行了，
> 之前封装的代码有问题，可以直接重构。」本稿只记现状解剖、目标形态与开放问题；
> 不写代码。建议时序：T40 W2（ApiError kind 文案表落地）之后启动——文案层先统一，
> 表面合并才不返工。

## 0. 现状解剖：一次「发送」穿过的模块（7 跳）

```
UI（ComposerRegion 发送按钮/回车）
 → composer/submit-composer-draft.ts   草稿清理编排
 → composer/submit-draft.ts            `! ` bash 前缀检测 + 空校验（deps.actions 反向注入——层次倒挂）
 → live/workspace-actions.ts           notifySubmitFailure 文案映射（面 65 个成员）
 → live/live-controller.ts             守卫/懒恢复/自愈/prompt 投递
 → live/client-invoke.ts               IPC
 → main api-routes 'session/prompt'    compact 词法拦截 / streaming_window 降级重试
 → hub
```

四个病灶：
1. **一个动词穿 5 个渲染层模块**；`! ` 直执行检测在 composer 层（应是发送服务内部路由）。
2. **层次倒挂**：submit-draft.ts 接收 `deps.actions` 回调上抛——底层模块调用上层动作。
3. **双表面动词二写**：workspace-actions 与 live-controller 每个动词各写一遍
   （submitDraft ×2、selectThinking ×2、stop ×2……），65 成员大杂烩面。
4. **文案映射散三处**：notifySubmitFailure（workspace-actions）、controller 内 pushNotice、
   strings 内 createFailed 分派——T40 W2 的 kind 查表会先统一这一层。

## 1. 目标形态（用户裁决 2026-09-21：「正常调用应该是 UI -> api -> hub」）

```
UI        渲染 + store 订阅（读路径），动作只调 api —— 一行：onClick={() => void api.session.send(draft)}
 ↓
api       @paiapp/api：动词面 + zod + ApiError + 管线（校验/恢复/自愈/超时/观测）
 ↓
hub       x-harness
```

两条物理事实吸收为 api 的**内部实现细节**，不是层：
1. **进程边界**：api 同一份接口、两种 transport 注入——renderer 侧是 IPC 代理，main 侧直连
   host port；UI 只见类型化动词（`api.session.send(...)`），IPC 方法名字符串只剩线上协议
   （api 包内部生成，两侧不再文本书写——§此前 defineRoutes 讨论随之溶解）。
2. **app 业务不再是层**：注册表/信任态/收养/白名单成为 api 动词的主进程侧实现体
   （动词 = 业务 + hub 调用，一个函数）；api-routes 作为层溶解——路由表变 api 方法注册表，
   业务函数变动词实现。

发送管线整体**主进程化**：空舞台守卫、懒恢复唤醒、unknown_thread 自愈（真相在注册表，
main 持有）收进 `api.session.send` 的主进程实现；renderer 的 queued-drafts 大半溶解
（streaming 窗口入队重试主进程既有）。渲染层只剩：组件 + store 折叠（读）+ 一行 api 调用（写）。

```
api.session.send 内部（主进程侧）：空校验 → `! ` 路由 → 空舞台守卫 → 懒恢复
  → hub prompt → streaming_window 降级 → unknown_thread 自愈 → kind→事件/回执 → 草稿清理回执
```

## 1.4 与 T40 的关系（合并后的终局）

T40 的 transport/ApiError/词表/码表对拍是这套模型的**骨干**（不变）；T41 从「渲染层收敛」
重定义为「**UI→api 直调 + 发送管线主进程化 + api-routes 溶解**」：T40 W2 之后，
api-routes 的方法注册与业务动词逐步搬入 @paiapp/api 主机形态，渲染层中间模块按 §1.5 删除。

## 1.5 删层判决（用户裁决 2026-09-21：「删除无用的中间层」）

| 中间层 | 判决 | 逻辑去向（唯一归宿） |
|---|---|---|
| composer/submit-composer-draft.ts | **删** | 草稿清理 = send 管线成功分支的一步 |
| composer/submit-draft.ts（作为独立模块 + deps.actions 反向注入） | **删** | `! ` 路由 + 空校验 + 图/bash 互斥 = send 管线前置步骤 |
| composer/queued-drafts.ts / queued-submit.ts（作为独立面） | **并入** | 流式排队 = send 管线的流式分支（语义保留：按线程暂存、轮末冲刷） |
| live/workspace-actions.ts（作为层） | **删** | 文案映射 → kind 查表（T40 W2 后一处）；编排动词 → pai 门面；纯透动词 → 直接绑定 |
| live/live-controller.ts（作为第二表面） | **收编** | 与上合并为**单一管线层**（守卫/懒恢复/自愈/水化/事件接线；文件可留作实现载体，表面只此一层） |
| live/client-invoke.ts、main api-routes、store 折叠机（fold-*） | **留** | 协议边界与读路径，不是中间层；lazy-resume 的去重/乐观登记语义原样保留 |

判「无用」的标准：该层拿掉后其逻辑有唯一归宿、调用方更简单、测试跟着动词走（迁移合
并，不删断言）。终态渲染层内**两层**（pai 门面 → 管线），发送链 7 跳收敛为：
`UI → pai.send → 管线（校验/路由/排队/恢复/自愈）→ IPC → 主进程路由 → hub`。

## 2. 开放问题（待讨论定稿）

1. **回执通道**：发送失败/成功对 UI 的反馈走事件推（notice/UiEvent，现状延续）还是动词
   返回值（IPC 回执）还是并存——倾向并存：事件推呈现、返回值供调用方附加反馈。
2. **queued-drafts 溶解边界**：排队真相主进程/hub 已有（steer/followUp 轮末消费），渲染层
   保留多少乐观 UI（排队卡片的即时呈现）待 R1 时定量。
3. **时序**：依赖 T40 W2（ApiError kind 与文案表）落地后启动；T41 全程不碰 hub 协议。

## 3. 波次草案（重定义后，讨论用，未定稿）

- **R1 骨架**：@paiapp/api 双 transport 形态（renderer IPC 代理 + main 主机注入 host port）；
  方法注册表从 api-routes 平移；发送动词主进程化（守卫/懒恢复/自愈迁移且测试随迁）。
- **R2 溶解**：api-routes 业务动词实现搬入 api 主机、路由表层删除；渲染层中间模块按 §1.5
  删除；UI 调用点全部换 `api.<域>.<动词>`。
- **R3 收口**：grep 断言——UI 零 import controller/actions/submit-*；IPC 方法名字符串仅存
  api 包内部；store 折叠面只读。

## 4. §2.2 裁决落地：排队卡片单条操作面（queue/drop、queue/send_now）

**裁决（2026-09-22）**：R1 溶解 queued-drafts 时 A7 的三个单条动作（立即改向/编辑/移除）
随本地暂存层一并消失，排队卡片退化为纯只读镜像——与本任务「流式排队 = send 管线的流式分
支」并存的用户操作面缺口。根治不在渲染层回退（本地暂存有丢失面，T11 已裁决接受），而是把
单条操作下沉为 hub 协议一等能力，条目 id 贯穿全链：

- **x-harness 侧**（queue-item-ops 分支）：
  - core/session `InboxSpliceData` 新增 `drop`（单条移除）与 `retarget`（单条改道，entry
    本体与 id 原样跨队列移动）两 op，WAL 形状门同步放行；与 `claim`（消费进上下文）严格区分。
  - agent-loop `chainsNextTurn` 计入 next-step：纯防御子句。现驱动流中该析取支实际不可达——
    completed 收轮前必经 stopping 窗口重读（stoppingResumes 读1/读2）与下一步 claimStepBatch，
    next-step 存货在那两处已被消费；改道/steer 条目的真实保障 = stopping 窗口（含 dispatch
    await 窗口内落 WAL 的 retarget）+ 下次 kick 的 step0 claimTurnBatch（含 next-step 全部）。
    保留子句防未来重构挪动收尾序列时开真实搁浅口。
  - hub 新命令 `queue/drop`、`queue/send_now`（entryId 寻址；entryId = get_state.queue 投影
    携带的 inbox entry id，与请求回执 id 不同名）。send_now 仅 followUp 条目可改向；无运行
    中轮（空闲且无在飞 send）按 `streaming_window` 族拒绝（条目留在队列不动）。
- **pai 侧**：
  - contracts：queueChanged / ThreadStateView.queue 从文本数组升级为条目数组（`QueueEntry`
    = {id, text}，叶子模块防循环导入）；`session/queueDrop`、`session/queueSendNow` 两动词。
  - main：队列镜像解析携带 id（垃圾条目防御过滤）；路由透传 hub 拒绝（state_conflict /
    streaming_window 原样上抛，消费方按码出文案）。
  - renderer：卡片动作接线——立即（仅生成中显示，改向当前轮步边界注入）/ 编辑（移除条目 +
    文本回填草稿槽，非空草稿追加不覆盖）/ 移除；点击竞态（条目恰已入轮）按
    `queuedEntryConsumed` 提示收敛，不再有静默失败。

**不处理**：steering 条目（next-step）的单条操作（本就不在卡片面渲染）；clear_queue 全清
的 UI 入口（单条删除已覆盖高频路径）；图片条目的编辑回填（仅文本回填，WAL 中原图保留）——
空文本条目（纯图）的编辑动作 = 仅移除不回填；改道后撞异常终态的可见性——send_now 改道进
next-step 后该轮若以 error/aborted 收尾，条目保留在 next-step（内核语义：异常终态不链），
无卡片呈现、待下次 kick 的 step0 顺带消费（与 steer 同型既有行为；内容与 id 不丢，内核
repair 对改道条目的回灌队列/顺序在 crash 恢复窗口可能漂移——可接受，不在本批处置）；
WAL 形状门对 `retarget.to = 原队列`、`dropped` 重复 id 不设限（合法生产者写不出，fold 语义
仍良定，作为损坏防线的收紧随缘）。
