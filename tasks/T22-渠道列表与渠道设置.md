# 渠道列表与渠道设置 方案

> 状态：已核销
> 级别：中
> 上游：T19（设置界面重构）、T20（子 Agent 管理，列表↔表单同款交互）、T21（模型选择统一 CommandDialog）
> 分工：本会话独立实施（无可用子 agent）。对抗审查原计划由独立 `pi -p` 会话执行（角色分离），
> 实测本机出口网络被拦（`curl https://api.openai.com` → `CONNECT tunnel failed, response 403`），
> 独立会话无法连模型，改为**同会话结构化对抗自查**（按「假设这段代码是错的」逐项审 diff，
> 结论见「对抗审查」节），受限事实如实记录，不冒充独立审查。

## 背景

设置页「模型」分区当前是「provider 卡列表 + 卡内展开表单」：新增/编辑共用 `provider-form.tsx`（156 行的
`providers-section.tsx` 负责列表态与编辑态切换），表单把 API 格式硬编码为 `'openai-completions'`，
模型清单以 chips 形式挤在一个输入框里。用户要求改成**渠道列表**：点击渠道进入详情，可设置
baseUrl、API 密钥、API 格式，并显示/增删模型清单；组件化、沿用项目现有 UI 风格。

## 契约

### 1. contracts：API 格式词表（新增，单一真相）

`packages/contracts/src/settings.ts`：

```ts
/** UI 可安全暴露的 API 格式子集（镜像 pi KnownApi；需特殊鉴权/私有协议的格式不进 UI）。 */
export const ApiFormatSchema = z.enum([
  'openai-completions',
  'openai-responses',
  'anthropic-messages',
  'google-generative-ai',
  'mistral-conversations',
]);
export type ApiFormat = z.infer<typeof ApiFormatSchema>;

/** 词表顺序即 UI 选项顺序（contracts 单一真相；文案在 strings）。 */
export const API_FORMAT_IDS: readonly ApiFormat[] = ApiFormatSchema.options;

export function isApiFormat(value: string): value is ApiFormat;
```

- **持久化形状不变**：`ProviderConfigSchema.api` 仍是 `z.string().min(1)`（宽松）。磁盘上手改过
  `pi-messages`/`azure-openai-responses` 等值不得因 UI 升级被判非法而整表降级（丢配置）。
  UI 选择器对非词表值**回退显示原值**（`apiFormatUnknown(value)`），保存时原样写回，不静默改写。
- `ProviderConfigView.api` 保持 `z.string()`，`provider/upsert` 入参形状不变（已含 `api`），
  主进程 `api-routes.ts`/`models-config.ts` 无需改协议。

### 2. 主进程：探活按 API 格式构造请求（变形，`apps/electron/src/main/provider-probe.ts`）

```ts
export function buildProbeRequest(input: {
  baseUrl: string; api: string; modelId: string; apiKey: string;
}): { url: URL; headers: Record<string, string>; body: string } | null; // null = 该格式不支持探活
```

| api | 路径（baseUrl 去尾斜杠后拼接） | 鉴权 | 请求体 |
| --- | --- | --- | --- |
| `openai-completions` / `mistral-conversations` | `/chat/completions` | `authorization: Bearer` | `{ model, max_tokens: 1, messages: [{role:'user',content:'ping'}] }` |
| `openai-responses` | `/responses` | `authorization: Bearer` | `{ model, input: 'ping', max_output_tokens: 16 }` |
| `anthropic-messages` | `/messages` | `x-api-key` + `anthropic-version: 2023-06-01` | `{ model, max_tokens: 1, messages: [{role:'user',content:'ping'}] }` |
| `google-generative-ai` | `/models/{encodeURIComponent(modelId 去掉 models/ 前缀)}:generateContent` | query `key=` | `{ contents: [{ parts: [{ text: 'ping' }] }] }` |
| 其他 | — | — | `null` → `{ ok:false, reason:'unsupported_api' }` |

- 实现上这张表是**单一真相**：`PROBE_SPECS`（键即支持的格式）给出 body/path/headers/query，
  `supportsProbe(api)` 与 `buildProbeRequest` 都从它派生，不再两处各写一份格式判断。
- URL 归一沿用现状：`new URL(baseUrl)` → 去 fragment → 去尾斜杠 → 拼路径；google 用
  `searchParams.set('key', …)` 覆盖既有 query。模型 id 的 `models/` 前缀会先去掉（官方文档常带，
  否则拼成 `/models/models%2F…` 打不到端点）。
- 错误映射新增 `unsupported_api`；其余 `provider_not_found / no_models / key_missing / busy /
  timeout / network_error / http_<status>` 不变。key 仍只出现在请求头/query，不进错误与日志。
- `ProviderProbeDeps.getProvider` 返回值增加 `api: string`。

### 3. 主进程：compat 门控（`models-config.ts`）

纯函数契约：

```ts
// api-format-options.ts
export function apiFormatOptions(current: string): { id: string; label: string }[]; // 词表 + 非词表回退项
export function apiFormatLabel(value: string): string;

// provider-editor.tsx（导出）
export type ProviderUpsertInput = { name: string; baseUrl: string; api: string; models: ProviderModel[];
  thinkingFormat: ThinkingFormat; apiKey?: string };
export function buildProviderSubmit(fields: {
  name: string; baseUrl: string; api: string; models: readonly ProviderModel[];
  modelDraft: string; thinkingFormat: ThinkingFormat; apiKey: string;
}): { ok: true; input: ProviderUpsertInput } | { ok: false; reason: 'incomplete' };
```

- `buildProviderSubmit`：name/baseUrl trim 后非空 + `models ∪ parseModelIds(modelDraft)` 非空，否则
  `incomplete`；`thinkingFormat` 仅当 `api === 'openai-completions'` 时透传，否则归 `'default'`；
  `apiKey` 长度 > 0 才带上（空 = 保持原值，与 `file-settings.upsertProvider` 语义一致）。
- **清除 key 独立于保存**：`provider-key-field` 的两步确认直接调用 `onClearKey()`
  （= 用磁盘现值 + `apiKey: ''` upsert），不受表单草稿影响；成功由 store 回流把 pill 翻成「未设置」。
- **保存后去向**：`onSaved(name)` 存在则调用（settings：编辑态停留详情、新建态切到新渠道详情）；
  不存在则清空字段（onboarding 复用，保持现状）。
- **删除只在列表卡**（两步确认）；详情页不重复放置删除入口。
- **测试连接只在详情页**（编辑态，渠道已落盘才可探活）；列表卡不再放测试按钮。
- **导航形态**：列表 → 钻入详情（面包屑返回），与 T20 agent 表单一致；不使用双栏/手风琴。

## 裁决

- 「用户裁决」交互形态 = 列表 → 钻入详情（用户原话「点击渠道，可以设置该渠道的…」；对照方案：
  双栏/手风琴被否，理由是设置页已有左侧导航，双栏会再挤一层）——默认裁决，否决窗口内可推翻。
- 「用户裁决」API 格式选项 = 上表 5 项子集（其余格式需特殊鉴权，选了也连不通）——默认裁决。
- 默认裁决：删除只在列表卡、测试连接只在详情页；编辑保存后停留详情（便于立即测试）。
- 默认裁决：非 openai-completions 隐藏思考形态并归 `default`；`thinkingFormat` 仍是持久化字段。
- 默认裁决：非词表 api 值回退展示原值，保存不静默改写。
- 默认裁决：内部命名保留 `provider`（域内单一术语），仅用户可见文案用「渠道」；不引入第二套领域词。

## 测试口径

- **契约**：`API_FORMAT_IDS` 长度与顺序 == `ApiFormatSchema.options`；`isApiFormat` 对词表/非词表判定。
- **表驱动（探活请求矩阵）**：5 种 api × {路径, 鉴权头/query, body} 逐项断言；未知 api → `null`
  → `unsupported_api`；`buildProbeRequest` 不把 key 写进 URL 之外的位置（google 场景 key 在 query）。
- **边界**：baseUrl 带尾斜杠/query/fragment；模型 id 含 `/` 与特殊字符（google 需 encode）；
  非法 baseUrl（`new URL` 抛错 → `network_error`）；空模型清单 → `no_models`；无 key → `key_missing`。
- **models-config**：openai-completions + 非 default 形态 → 写 compat；非该格式（anthropic）→ 不写；
  default → 不写。
- **纯函数**：`buildProviderSubmit` 必填/归一/思考形态门控/apiKey 省略；`parseModelIds` 全角逗号/
  换行/空白；`mergeModelIds` 去重保序；`apiFormatOptions` 词表 + 回退项；`apiFormatLabel` 未知值。
- **SSR 冒烟**：渠道列表（空态/有渠道/搜索无结果/添加按钮）；渠道详情（编辑/新建两态、字段标签、
  非 openai 格式时无思考形态、非词表 api 回退项、key pill、模型行）；编辑器保存失败文案。
- **回归**：旧 `provider-form.test.ts` 迁移为 `provider-editor.test.ts`（同名断言不删）；新增
  「非 OpenAI 格式探活不再误报 network_error」回归（症状名入用例名）。
- 分层：单元（纯函数/探活矩阵/序列化）+ SSR 冒烟（渲染层）；无跨进程 e2e 装置，交互链路真机走查
  （与 T20/T21 同口径）。
- **无 DOM 环境下的回调接线**：项目无 jsdom/happy-dom，SSR 只验证输出；新增
  `__test__/element-props.ts` 把组件返回的元素树摊平为 props 列表，直接触发 `onClick`/`onChange`/
  `onKeyDown`/`onSelect`，验证「事件 → 回调」接线（前提：被测组件自身不调 hooks；含 `useState` 的
  组件仍靠 SSR 冒烟 + 真机走查）。已用于模型行、模型清单、`TextField`/`SelectField`。
