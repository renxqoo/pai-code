## 0. 症状判定（用户现场 + 已入库红测）

用户现场：**对话进行中（模型流式输出中）刷新页面 → 本轮已经输出的内容丢失、只剩最新输出；轮结算/任务完成后内容又完整。**

已入库的红测（对修复前代码全红；实测输出）：

| 用例 | 位置 | 实测 |
| --- | --- | --- |
| 症状回归「刷新后已经输出的消息丢失，只剩最新输出」（事件先落再对账） | `live/__test__/fold-hydrate.test.ts` | `Expected to contain "前半" / Received "看一下天气\n后半"` |
| 症状回归「刷新后已经输出的消息先显示再消失」（对账先落、事件后到 → 补挂重定基收回） | 同上 | 同上 |
| 症状回归「刷新后在途轮只剩最新输出」（全链路：event + `ensureHydrated`） | `live/__test__/controller-lazy-resume.test.ts` | `Received "后半"` |

## 1. 根因（两半，分属两个仓库）

**半边一（app，本任务 P0）——已落盘内容被折叠层丢弃。** 转写（`get_entries`）里本轮已完成的 assistant 消息与工具结果**都在**；问题出在 `foldHydrate` 的 `hydrate/reconcile` 分支（`fold-events.ts:153-208`）：只要 `state.liveTurnId !== null` 就 `inFlightOwned = true`（连 `streaming` 都不判断），于是「末位用户消息之后的转写条目」被**整段丢弃**（`:174-177` 不插入、`:204` 不记 seen），已先落库的同类前缀轮按派生 id 收回（`:181-183`）。两条时序（事件先落 / 对账先落）都收敛到丢内容。该规则由 `d614997`（T34 §6.6）引入，**修复前是「照常插入」**（表现为同轮双渲染），即本次症状是那次修复的回归：它用**删数据**换了「不双渲染」。

**半边二（hub，T35 依赖的协议变更）——在途内容无读口。** 刷新前已流出的在途内容只活在 worker 内存（`agent.state.streamingMessage`），盘上未落（`message_end` 才 `appendMessage`）、事件流不重放、`get_messages` 也不含 partial —— 客户端在信息论上无法恢复。详见 hub 方案 §一/§二。

两层不可互相替代：只修 hub 不修 app，刷新后本轮更早的 assistant 消息与工具卡片**依旧整块消失**；只修 app 不修 hub，在途消息的前半段依旧缺失。轮结算时 `turnStartCursors`（controller 闭包 Map，重载即空）取不到本轮游标 → `since=null` → 全量 `hydrate/rebuild` 替换 → 内容恢复，这正是「对话结束、任务完成又完整了」。

## 2. 外部契约（T35）

### 2.1 块身份统一为消息时间戳（`messageTs`）

- 两个来源的块 id 必须同源：live 侧早已用 `String(message.timestamp)`（`packages/adapter/src/event-mapper.ts:198-202`，`messages_start/update/end` 的 `messageId`）；转写侧目前用**条目 id**（`hydrate-items.ts` `text-${item.id}`，条目 id 是 8 位 hex）。
- 变更：adapter 从 `entry.message.timestamp` 取 `messageTs` 暴露到 assistant `HistoryItem`；`buildTurnBlocks` 的块 id 统一为 `text-/think-/tools-<messageTs>[<序号>]`。
- 兜底：legacy 条目无 `message.timestamp` → 回退条目 id（退化为现行为）；同毫秒碰撞 → 追加条目序后缀（保留既有 `-${turnIndex}` 兜底语义）。
- 收益：同一消息在「转写 / 在途快照 / 增量流」三源恒为**同一块 id** → 合并幂等，双渲染被结构性排除（不再靠删内容）。

### 2.2 转写尾 span 合入在途轮（不再丢弃）

| 情况 | 处置 |
| --- | --- |
| 转写条目在本轮起点**之前** | 照旧按「未见过的前缀」插入（历史轮） |
| 转写条目在起点之后、且是 `message` 条目 | 作为普通条目插入（用户回显 / 轮内注入 / steer），去重按条目 id |
| 转写条目在起点之后、且是 assistant/bash 条目 | **块合入在途轮**（按块 id 幂等并集）；若此前已作为独立前缀轮落库，先合内容再按 id 收回 |
| 无在途轮（`liveTurnId === null`） | 照旧正常插入（不涉及归属） |

- **本轮起点的权威来源 = hub 读口的 `get_inflight.turnStartEntryId`**（不是「末位用户消息」启发式）：轮内注入的 user 消息（task-notification/task-message，origin=system）与 steer 中途插话都会让启发式把同一轮切错，切错就是双渲染。
- **错配退避（三种都要定义，缺一即隐藏职责）**：① 客户端 live、hub 已 settle（`turnStartEntryId === null`）→ 无在途轮归属，尾 span 按普通前缀插入；② 客户端 idle、hub 在途（重载后未收到任何事件）→ 以 `turnStartEntryId` 为准建立归属，`message` 直接建块（`get_inflight.message` 的 `timestamp` 就是 live 块 id）；③ 读口不可用（旧 hub / 能力探测失败）→ 见下条降级。
- **工具调用按 `callId` 逐条裁决，权威序（修正版）**：
① `callId ∈ get_inflight.toolOutputs`（hub 说它**正在跑**）→ **running + 快照输出**，凌驾于转写分支之上（时长用 `startedAt` 复原）——转写里同名 callId 可能只是「assistant 消息已落盘、toolResult 未落」，采信它会把还在跑的工具砸成「完成 + 空输出」的假完成态（`entries-mapper.ts:81-89` 对「结果未落」与「跑完但输出为空」不可区分）；
② 否则 live 轮已有该 callId（事件流折出，含 `tool_ended` 权威 output 与客户端测得的 `durationMs`）→ 保留 live；
③ 否则 live 无、转写有 → 用转写（其 output 来自 toolResult 条目）；
④ 都没有 → 不产生块。
- **seenIds 维持「尾 span 不记」**：记了会在「settle 重建失败（`hydrate/failed`）→ 下一轮 `turnStarted` 退役旧 live 轮」路径上二次丢失；不记则靠独立插入自愈，去重交给幂等并集。
- bash 条目在 span 内 → 其工具块合入在途轮（live 轮不产生 bash 块，无双渲染面）。

### 2.3 统一收敛链（读口族 + 幂等合并 + 读序规则）

**收敛链 = 订阅先建立 → 内存态读在前 → 落盘读最后**：先 `session/inflight`（在途消息 / 工具在途输出 / bash 在途 / 本轮起点）+ `session/state`（含 `queue`）+ `session/subagents` + `session/dialogs`（待定弹窗），**最后**才 `session/entries`（落盘真相）。顺序不是风格问题：worker 的落盘是「先发 `message_end` 事件、再 `appendMessage`」两步（`agent-session.ts:679` 先于 `:698`），若先读 entries 后读 inflight，「恰在读之间结束的消息」两边都拿不到——读序规则把它压到单侧（后读的 entries 必然包含它）。**兜底规则**：`turnStartEntryId !== null`（轮在途）而 `message === null` 且视图内没有该轮的终态块时，**复拉一次** `session/entries`。合并规则全部幂等（表见 hub 方案 §3.1 登记表；实现落 `fold-hydrate` 与 `hydrate-items`）。

服务对象（同一条链，不各写一份）：首挂载激活、渲染层重载（`ensureHydrated`）、宿主重启回落、`force` 重试入口、以及不需要重载也能自愈的补拉入口（bridge 抖动 / StrictMode 重挂）。

**合并规则（按源，与实现逐条对齐）**：在途消息与 live 块同 id → 文本/思考走 **append-only 拼接**（一方是另一方前缀取长者；一方是另一方**后缀**（快照晚于增量）取快照；互不为前后缀则「转写/快照 + live」拼接——直接拼接会在快照晚于增量时重复已收内容）；工具调用按 `callId` 合并且**读口说在跑就置 running + 快照输出**（权威序凌驾于转写：转写对「结果未落」与「空结果」不可区分）；`queue` 整体替换；`dialogs`/子代理快照**只增不删**（快照读取与应用之间存在在途窗口，凭快照删除会复活刚结算的弹窗/误删本地态——删除只走 `dialogSettled` 与注册表自身收敛）。

**降级（读口不可用时的行为必须写死，否则是隐藏职责）**：hub 不支持某读口（命令 failure）→ 控制器探测一次并缓存「不可用」，该读口跳过；**降级下尾 span 仍走幂等合入（不退化为 §6.6 的丢弃）**，只是**轮边界退回「末位用户消息」启发式**（轮内注入/steer 场景存在切错风险，属已知降级损失，登记在此）；在途前缀（未落盘那半段）与队列/弹窗/子代理无替代来源，等于维持今天的行为。两条硬约束：① **探测只允许对 live 会话发起**——对 parked 线程发未知命令会经 hub 的 passthrough 走唤醒路径（`host.ts` handlePassthrough → `sendToThread` ensureAwake），违反 T27「读不唤醒」；② **不得按版本号比较**（能力位是后端能力面，不是 hub 版本面），探测结果按 hub 进程代际失效（host restarting/failed 后清空重探）。

### 2.4 本轮游标改为读口事实（性能，单轨）

`turnStartCursors` 目前是事件派生（`turnStarted` 记录、settle 消费）；重载即丢 → 第一次 settle 退化为 `since=null` 全量拉取（长会话 O(全量)）。

**单轨改法**：`turnStarted` 时随对账并行读一次 `session/inflight`，把 `turnStartEntryId` 存进线程折叠态（`LiveThreadState.turnStartEntryId`），settle 窗口重建与尾 span 归属**共用这一个事实**；`turnStartCursors` 闭包 Map 删除。读口不可用时该字段为 null → settle 退化全量（现状行为，可接受）。**不得**保留「事件游标 + 读口」双轨（违反单轨纪律，且两条来源在重载场景必然分叉）。

## 4. 并发/一致性预算

- **app 侧新增常驻状态**（均为有界且回收路径完整，见 §9）：① 读口可用性缓存（`ReadPorts` 实例内的 Set，宿主代际变化清空）；② bash 收尾探测定时器（每线程至多一条、有界重排 ≤30 次、dispose/宿主消亡/线程消亡/`runBash` 结束四条路径回收）。主进程零缓冲。
- **收敛链**：并行 ≤5 条只读命令、单条载荷上界见 hub 方案 §3.2；本地 P95 目标 < 20ms/条、整链 < 150ms（含 IPC，不阻塞首屏——转写先渲染，其余幂等合入）。
- **幂等性**：任意交错（快照先 / 增量先 / 交错）与重复应用结果一致 → 写成表驱动用例（三种交错 × 重复调用）。
- **不变量**：同一轮恒只有一个渲染体；历史轮不被误伤；`data-*`/React key 只依赖块 id（换 id 只引发一次 remount，见对抗审查结论）。

## 7. 对抗审查预置攻击面（独立会话必审）

1. 块 id 换名波及面：fork/reveal（用条目 id）、React key、`hydrate/initial` 与 `rebuild` 的同批切换、既有断言清单。
2. 尾 span 合入的边界：本轮起点判定（`turnStartEntryId` 缺失/为 null 时如何退避）、span 内的 message/bash 条目归属、已落库前缀轮的收回时机。
3. tools 合并权威序的三条分支（running 不掉完成态、durationMs 不丢、快照补缺）。
4. seenIds 与 live 轮退役（settle 重建失败 → 下一轮冻结/移除 live 轮）的交互。
5. 收敛链并发：读口返回与新事件交错的幂等性；宿主重启中读失败；能力探测失败缓存不被误清。
6. 性能：重载链命令数/载荷上界；settle 从全量拉取改为窗口拉取后的语义等价性测试。
7. 读序与兜底：先 entries 后 inflight 的错序是否真能丢内容（用快照-快照交错用例反证）；复拉兜底的触发条件是否过宽（误拉全量的风险）。
8. 读口不可用路径：降级是否真的回到 §6.6 现状且**不唤醒 parked**；探测缓存的失效时机（hub 重启后是否重探）。

## 11. 用户现场回归（2026-09-11 夜：多次刷新后「思考只剩碎片」「轮计时从 0 开始」）

真机复现路径：长轮次中反复刷新 → 屏幕上只留下刷新后的增量（思考只剩尾段如 "to the"），且轮计时从刷新时刻重新起算。

**根因（一个守卫过严 + 一个事实缺失）**：

1. **守卫过严把当前轮的在途快照误丢**：`snapshotFresh` 原先要求「本地从未结算过（`turnsSettled === 0`）或有同轮边界」。刷新后只要先收到上一轮的 `turnSettled`（`turnsSettled` 变 1）而本地尚无边界，当前轮的在途快照就被整批丢弃 → 只剩刷新后的增量（碎片）+ live 轮新建（计时从 0）。**修正**：只有「读在途期间发生结算」才算过期——host 的应答反映**读取时刻**的状态：结算先于读发起时，那次读之后要么没有在途轮（空形态）、要么是结算后新起的轮（当前真相），不可能是已结算轮的旧面。用例改写为真实竞态（读在途期间结算 → 丢弃）+ 空形态不点亮两例。
2. **轮计时没有跨刷新的事实**：live 轮的 `startedAt` 取「本渲染层看到第一个事件的时刻」，重载后必然从 0 起算。**修正**：hub 的 `get_inflight` 新增 `turnStartedAt`（与 `turnStartEntryId` **同点采集**于 `agent_start`），客户端用它续算；**老 hub 兜底**：读口不给该字段时，用转写里本轮 prompt 的提交时刻回填锚点（与 `hydrateItems` 的轮计时锚点同源，只回填更早值）。
3. 顺带修掉一处显示瑕疵：在途消息正文为空（思考先行）时不再建空正文块——否则正文位置会多出一行空行。

**新增回归用例**（`convergence-reload.test.ts`，共 23 例）：思考碎片合并（快照全文 vs live 尾段必须合成完整思考）、读在途期间结算 → 丢弃、结算后空形态不点亮、`turnStartedAt` 续算计时、老 hub 锚点回填。

## 12. 用户现场回归（2026-09-12：多次刷新后消息只显示中段片段）

真机现场：会话 `01a09136`（300840 股票查询）流式中多次刷新，完成后该消息的思考块仍只显示 ". This is an A-share stock ("（落盘思考全文的中段切片：前缀 "The user pasted…300840" 与后缀 "创业板 ChiNext…" 均丢失）。

**根因（空 id 增量的匿名块孤儿）**：hub 的 wire 剥离（`event-strip.ts`）把 message_update 的 `message`/`partial` 整体剥掉——重订阅后续上的 delta 全部**空 messageId**，折叠层以 `liveMessageId` 兜底；而重载落在消息流式中时 `message_start` 已随旧渲染层消亡，`liveMessageId` 要等收敛读口响应（bootstrap + 四读 round trip，慢于首批 50ms 事件批次）或 `messageFinal` 才能确立。身份确立**之前**折出的增量落成匿名块（`think-`/`text-`/`tools-`，空 id），此前的实现没有任何路径认领它们：

- `applyInflight` 按 `think-${messageTs}` 寻址建块 → 与匿名块互不相认，同一条消息渲染成「中段孤儿片段 + 正常块」两个体；
- `messageFinal` 的权威替换同样寻址不到匿名块；
- 只有 settle 的全量重建兜底能抹掉孤儿（重建失败/降级即永久滞留）——用户看到的正是孤儿块本身（重订阅到读口响应之间收到的那一两批 delta）。

§11 的修法（snapshotFresh 放宽 + turnStartedAt）解决的是「快照被误丢」；本条是另一个独立洞：**快照即使正常落地，也合并不进先到的匿名块**。既有测试全部给 delta 显式 id，与真实 wire 形态不符——这是假绿的直接来源。

**修法（身份确立即认领）**：`turn-ops.claimAnonymousBlocks(blocks, messageKey)`——消息身份确立的两个时点（`applyInflight` 建立快照身份、`messageFinal` 权威身份）把匿名块归位到 `*-${messageKey}`：text/thinking 走 append-only 合并（匿名块是重订阅后的增量，与快照必为前后缀关系）、tools 按 callId 并集（`unionToolCalls` 单一实现，`merge-turn-blocks` 同步复用）。幂等：无匿名块原引用返回。认领后 `liveMessageId` 同步确立，后续空 id 增量直接进正确块。

**新增回归用例**（`convergence-reload.test.ts`，4 例，全部以真实 wire 形态（空 messageId）驱动）：空 id 思考增量先到 + 读口快照后到 → 恰一个思考块且为权威全文；老 hub（读口不可用）匿名块由 messageFinal 认领；空 id toolcall 不双渲染；编排级竞态（重订阅首批事件先于 ensureHydrated 读口响应——用户多次刷新命中的时序）。
