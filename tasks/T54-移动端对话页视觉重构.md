# 移动端对话页视觉重构：建立层级

> 状态：草稿（bw 真机量测驱动）
> 级别：中（不改信息架构，重做排版层级）
> 范围：`apps/mobile` 聊天页排版

## 1. 问题（bw 真机量测，非主观判断）

在 `expo start --web` + bw（390pt 视口）实测当前渲染，逐项取到客观数据：

| 元素 | 实测字号 | 实测颜色 | 问题 |
|---|---|---|---|
| Agent 正文 | 15px | `rgb(16,16,18)` | — |
| 用户输入 | 15px | `rgb(16,16,18)` | **与正文完全同色同号** |
| 列表项 | 15px | `rgb(16,16,18)` | 同上 |
| 状态行「共工作 4m 13s」 | 13px | 灰 | — |
| 「· 改了 N 个文件」 | 11px | 灰 | — |

**核心病灶：正文 / 用户输入 / 列表项三者同字号同颜色，层级被拉平。** 用户输入是「别人说的话」，
Agent 正文是「系统对你说的话」，视觉上却完全一样——用户无法一眼分辨哪段是任务、哪段是回答。

另有三条实测发现：

1. **无 `aria-expanded`**：实测 `document.querySelectorAll('[aria-expanded]').length === 0`。
   移动端所有可展开行（状态行、组头、执行行）都没有展开态语义，TalkBack/VoiceOver
   读不出「可折叠」；自动化也无法定位（本次走查脚本因此点不开任何折叠）。
2. **过程刷屏**：一轮内 4 个编辑调用逐行平铺，每行一个图标+前缀+路径，纵向占满。
   PC 端同场景是「一行组头 + 点开看详情」，移动端没有组头聚合。
3. **缺少 44pt 触控区验证**：`layout.minTouch: 44` 已定义，但执行行的实际可点高度未量过。

## 2. 契约

不改信息架构（`@paiapp/ui-thread` 派生层、批次聚合、详情 Sheet 全部保留），
只重做**排版层级与交互语义**：

- `type` 层级重新分工（见 §4 裁决）：用户输入与 Agent 正文必须可分辨。
- 所有可展开行补 `accessibilityState={{ expanded }}` + `accessibilityRole="button"` +
  `accessibilityHint`（展开/收起后的去向）。
- 执行行触控区 ≥ `layout.minTouch`，用 `hitSlop` 补足视觉高度不足的行。
- 过程区在移动端默认收起（同 PC），组头一行承载聚合信息。

## 3. 问题域

处理：字号/颜色/间距的层级分工、用户输入与 Agent 正文的视觉区分、过程折叠密度、
可展开行的无障碍语义、触控区尺寸。

不处理：数据通路（仍 fixture 驱动，不接 hub）；Markdown 渲染器能力；
输入区与会话列表（本轮只做聊天页时间线）；深色主题（跟随现有 token，不新增语义）。

## 4. 裁决

**字号分工（用户裁决：层级要能分辨）**

- Agent 正文：`type.body` 15px —— 主要阅读对象
- 用户输入：**15px 但换视觉载体**（保留字号，靠背景卡 + 左侧色条区分）。
  用户输入是「任务卡」不是「引文」，缩小字号会让长任务描述难读；
  真正的层级差靠**载体差**（卡面 + 边条）而非字号差。
- 列表项 / 引用：`type.row` 13px（现在错误地用了 body 15px）
- 过程行（状态行、组头、执行行）：`type.row` 13px
- 元信息（耗时、文件计数）：`type.meta` 11px

**颜色分工**

- Agent 正文：`colors.text`（近黑）
- 用户输入卡：`colors.textSecondary` + `colors.surfaceSubtle` 背景 + `colors.borderStrong` 左边条
- 过程行：`colors.textMuted`（现在已是灰，保留）
- 失败行：`colors.destructive`（保留）

**过程折叠（对齐 PC）**

- 轮级状态行「共工作 Xm」常显箭头（触屏无 hover，不能靠 hover 提示可展开）
- 一轮内 ≥2 条工具调用 → 一行组头（复用 `toolGroupLabel`），点按展开
- 批次内各调用行：前缀 + 目标，不再逐行平铺到默认视野
- 失败批次默认展开（错误必须可见）

**无障碍**

- 每个可展开行：`accessibilityRole="button"` + `accessibilityState={{ expanded }}`
  + `accessibilityHint`（"展开查看执行详情" / "收起"）
- 这不只是合规：本次 bw 走查脚本就是靠 `[aria-expanded]` 定位的，缺失导致自动化不可用

## 5. 实施顺序

- M1 建立排版基线：`type` 分工落到各组件，列表项降到 13px。
- M2 用户输入视觉分化：卡面 + 左边条 + 次级文字色。
- M3 过程折叠：组头聚合 + 轮级常显箭头 + 失败常开。
- M4 无障碍语义 + 触控区：全部可展开行补 `accessibilityState`，行高补 `hitSlop`。
- M5 bw 走查验证 + 移动端 jest 全绿。

## 6. 测试口径

- 快照/DOM 断言：用户输入与 Agent 正文容器样式不同（背景/左边条）
- 列表项字号 ≤ 13（`type.row`），不再与正文同级
- 过程区：≥2 工具调用渲染一行组头；组头有 `accessibilityState.expanded`
- 失败批次默认展开、成功批次默认收起
- 全部可展开行都有 `accessibilityRole` 与 `accessibilityState`
- 既有 jest 全量重跑（`bun run test` in apps/mobile）
