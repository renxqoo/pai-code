## 三、批次 1b 方案（小级 · design-a）

> 状态：已核销（2026-09-08，验收清单逐项通过，见批次提交）。UI 展示组件由 ui-coding agent 实现，主会话审查修正（引号风格归一、重命名输入补 select-text）并负责接线与测试。
> 级别：小（纯渲染层加法 + 既有 action 暴露；无新外部契约）

### 契约

- `filterSessions(sessions: readonly SessionCardModel[], query: string): readonly SessionCardModel[]`（新文件 `sidebar/filter-sessions.ts`）：trim 后空查询原样返回（同引用）；非空查询按 `title` / `projectName` 大小写不敏感子串匹配。
- `LiveController.compact(threadId): Promise<string | null>`（原 `Promise<void>` 升级）：成功返回 null，失败返回原因（与 `submitDraft` 同形）；hook 层转 notice。
- `LiveWorkspaceView.actions` 新增 `renameSession(threadId, name): Promise<boolean>`（controller 已有 `session/setName` 通路，hub 回推 `session_info_changed` → `sessionRenamed` 事件 → store 更新标题，无乐观更新）。
- UI 契约：搜索行受控输入（value/onChange/清空按钮）；会话卡 hover 重命名（铅笔入口 → 行内输入，Enter 提交 / Esc 取消 / blur 提交，trim 空值=取消）；assistant 正文块 hover 复制按钮；composer 动作行新增「压缩」图标按钮（compacting 时禁用）；access 选择器全链路删除（含 demo 夹具与 `composer.accessMenu` 文案）。

### 问题域

- 处理：过滤会话列表、重命名会话标题、复制 assistant 正文、手动压缩上下文、删除假 access 选择器。
- 不处理：跨会话全文搜索（属 A2/N 范畴，消息内容经标题间接覆盖）；重命名失败重试 UI（notice 提示即可）；compact 拒绝原因的专项文案映射（hub 无稳定字面量，通用原因提示，出现稳定字面量后补回归）；排队消息管理（A7）。

### 裁决

- 全部为讨论已定默认裁决的落地（见上表 #5/#8），用户已确认方向（2026-09-08 会话）。

### 测试口径

- `filter-sessions`：空查询同引用返回 / 空白串等价空查询 / 大小写不敏感 / title 命中 / projectName 命中 / 无命中空数组 / 中文与 unicode。
- `controller.compact`：成功 → null；失败 → 透传原因（fake client 表驱动）。
- `controller.renameSession`：成功 → true 且发出 `session/setName`；失败 → false。
- store `sessionRenamed` 折叠已有覆盖（store.test.ts）；组件视觉交互不新增测试装置，由既有 demo 装置回归。

## 四、批次 1c 方案（中级 · design-b）：设置容器 + D3 + D1 + D2 + J1

> 状态：定稿
> 级别：中（跨模块、新 UI 容器、新增契约面：provider/test 与应用偏好读写、主进程 HTTP 探活新面）

### 契约

- **容器**：`SettingsSheet`（420px 右抽屉）→ `SettingsScreen` 全屏 overlay + 左侧分区导航。分区集合（本批次落地前四个，后三个占位不渲染）：`providers`（Providers 与模型，D1）、`keys`（官方 API Key，D3）、`history`（历史，迁移）、`general`（通用，J2 落地时填充）。Esc 链路扩为：对话框 → 设置开 → 面板 → 停止。
- **D3**：沿用既有契约 `auth/list`（CredentialView[]）、`auth/setKey {provider, apiKey}`、`auth/removeKey {provider}`（main 已翻译）。hub 侧约束（design.md:63-76）：provider 必须是 hub 内置模型目录名（自定义 provider 拒绝，U11）；非 api_key 凭据受保护（set/remove 拒绝）；remove 幂等。渲染层 store 新增 `credentials: readonly CredentialView[]`（bootstrap 时拉取 + 手动刷新）。
- **D1**：provider 编辑 = 既有 `provider/upsert`（name 键 upsert，表单预填）；单模型增删 = upsert 的 models 数组编辑；默认模型 = 应用偏好（下条）；**连接测试** = 新契约 `provider/test {name}` → main 进程直发 OpenAI 兼容探活（POST `{baseUrl}/chat/completions`，max_tokens=1，携带 safeStorage key），结果判别联合 `{ok:true, latencyMs} | {ok:false, reason}`。不经 hub、不落任何状态；10s 超时；同 provider 单飞（在途再触发直接返回 in_progress）。
- **应用偏好**：`SettingsSchema` 增 `defaultModel: z.string().nullable().default(null)`、`onboarded: z.boolean().default(false)`（strict schema 扩字段，旧文件缺省回填）；`BootstrapViewSchema` 增 `preferences: { defaultModel: string | null; onboarded: boolean }`；新契约 `app/setPreference`（partial 写，`{defaultModel?}/​{onboarded?}`）。
- **D2**：composer 模型选择器 `modelOptions` 为空时触发器呈现引导态（点击回调 `onOpenSettings`）；思考档 `effortOptions` 为空时禁用并给 title 原因。
- **J1**：bootstrap 完成且 `!onboarded` 时进入全屏引导（app 屏幕态，非弹层）：步骤 1 配 provider（复用 D1 表单）→ 步骤 2 选默认模型（get_models 结果选择）→ 步骤 3 默认工作目录 → 完成（写 `onboarded:true`）。每步可跳过（Skip 进设置）；失败不阻断（引导完成判定以 onboarded 写入为准，provider 可为空）。
- 错误形态：全部沿用 `{ok:false, reason}` 中性英文 reason；用户可见文案进 strings。

### 问题域

- 处理：设置 IA 重构、官方凭据列表/录入/移除、provider 编辑与模型增删、连接探活、默认模型偏好、首次引导、空态引导。
- 不处理：hub 内置 provider 目录枚举展示（协议无命令，D3 用自由名输入 + reason 透传；目录枚举列为 hub 缺口候选）；provider/test 对非 OpenAI 兼容 api 形态的探活（api 字段当前恒 openai-completions）；OAuth 类凭据的录入（hub 拒绝，UI 只透传原因）；引导中途的模型拉取失败重试 UI（跳过即可）。

### 并发/一致性预算

- 探活：超时 10s；同 provider 单飞；并发不同 provider 上限 3（排队外直接拒绝 busy）；探活不阻塞设置页其它操作。
- 偏好写：settings.json 原子写（临时文件 + rename），读改写在 main 进程序列化（单实例锁内）。
- provider 变更引发的 host 重启沿用既有热判断通路，不在本批次改动。

### 拆分

- `packages/contracts`：settings.ts 扩字段；api.ts 增 `provider/test`、`app/setPreference`、BootstrapView 扩 preferences。
- `apps/electron/src/main`：api-routes 增两方法；`provider-probe.ts` 新文件（fetch 探活，唯一 HTTP 出口）；file-settings 扩字段。
- 渲染层：`settings/` 目录重组（settings-screen 容器 + 分区组件 + 导航）；`onboarding/` 新目录（向导屏）；live store 扩 credentials/preferences；hook 暴露对应 actions。
- 依赖方向不变：renderer → contracts ← main。

### 实施顺序（每阶段独立提交）

1. **1c-1 容器重构**：SettingsScreen + 分区导航 + Providers/History 迁移 + Esc 链扩展（纯 IA，无新契约）。验收：现有 provider CRUD/历史回归全绿。

4. **1c-4 D2**：composer 空态引导。
5. **1c-5 J1**：onboarding 向导 + app 屏幕态接线。
6. 收口：对抗审查（契约/并发面）+ 覆盖率复核。

- 连接测试走主进程直发探活而非 hub prompt（避免占用会话与预算；hub 无 per-provider 校验命令）——默认裁决，否决窗口至 1c-3 实施前。
