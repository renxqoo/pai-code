# 移动端对话页重构：对齐 PC 端信息架构

> 状态：定稿（PC 端对抗审查结论已落地——thread 执行展示系列修复提交即其产物）
> 级别：大（跨端共享包新增 + 移动端聊天页重写 + 旧实现删除）
> 范围：`packages/ui-thread`（新包）、`packages/contracts`、`apps/electron` 渲染层、`apps/mobile` 聊天页

## 1. 关键发现（决定了方案形状）

**发现一：移动端是 fixture 驱动的 UI 原型，不是 hub 直连。**
`apps/mobile/src/types/domain.ts` 的 `ChatMessage` 是扁平模型
（`kind`/`text`/`title`/`summary`/`status`），数据来自
`fixtures/agent-conversation.ts`，没有 `editHunks`/`subagents`/`diff`
这些结构化字段，也没有任何 hub 通路（`grep hub|getEntries` 只命中 `turns.ts` 的注释）。

**发现二：PC 端的派生逻辑几乎纯，唯一耦合是 `copy`（文案表）。**
`tool-summary.ts` / `tool-kind.ts` / `hunk-lines.ts` / `file-object-name.ts` /
`edit-file-groups.ts` / `call-detail.ts` 零外部依赖；`tool-group-summary.ts` /
`tool-row-label.ts` 只 import `copy`。这意味着**不该复制逻辑到移动端，而该抽成共享包**。

**发现三：图标与开合策略是「一半语义一半平台」。**
图标语义（哪类工具配哪支图标）是纯派生，图标组件（lucide-react 与
lucide-react-native）是平台件；开合策略（失败必见、运行中常开）是纯策略。
前者拆成语义键 + 各端映射，后者整块下沉，均不留双份。

## 2. 契约

**`packages/contracts` 增补**（类型单一真相，与 `ToolCallView` 同处）：

- `ToolCallStatus = 'running' | 'ok' | 'failed' | 'stopped'`：工具调用展示
  状态词表（渲染层状态机派生，非零退出必须区别于成功）。

**新增包 `packages/ui-thread`**（React 无关的纯派生层，PC 与移动端共用；
只依赖 `@x3code/contracts`）：

- `ToolKind` + `toolKindOf(name)`：工具名 → 类别（edit/write/read/bash/search/list/subagent/other）
- `toolPreviewMono(kind)`：摘要是否等宽字体
- `toolSummary(argsPreview)`：命令摘要——**忠实展示**：去整行 shell 注释 +
  折平空白与换行；不做任何内容改写与长度截断（截断是视觉层的事：PC 交给
  CSS truncate、移动端交给 numberOfLines，按真实渲染宽度裁剪）
- `toolIconKey(name)` / `toolGroupIconKey(calls)`：类别图标语义键
  （pencil/book/terminal/wrench）；图标组件由两端各自映射
- `toolGroupBuckets(calls)` / `toolGroupLabel(calls, copy)` / `toolGroupStatus(calls)`：
  并行批次 → 类别桶 / 组头标题 / 聚合态
- `toolGroupIsParallel(calls)`：≥2 才算批次
- `toolRowLabel(name, status, copy)` / `toolRowLabelOf(call, copy)`：执行行前缀
  （成功过去式 / 运行中进行时 / 失败「运行失败」/ 停止）
- `hunkLines(hunk, index)` / `allHunkLines(hunks)`：补丁片段 → 展示行
- `groupEditsByFile(calls)`：同文件多次编辑 → 按 path 归并的 diff 组
- `objectName(path)`：路径 → 文件名
- `callExpandable` / `autoOpenForCall` / `autoOpenForGroup` / `detailOutput`：
  工具详情展开条件与自动开合策略（失败必见、运行中常开、成功收起；
  手动意图优先于自动）
- `changedFileCount(calls)`：轮级变更摘要（成功编辑按路径去重的文件数，无变更为 null）
- 文案注入：以上涉及文案的一律**不直接 import copy**，接收
  `ToolCopy` 结构化文案表（group* 短语 8 键 + row* 前缀 21 键），
  由两端各自的 strings 适配层提供（PC 由 `copy.flow` 按 locale 取值组装，
  移动端由 `strings/zh.ts` 常量表提供）。

## 3. 问题域

处理：移动端聊天页的执行过程信息架构（并行批次聚合、类别图标、状态前缀、
失败文案、文件级 diff 合并、命令摘要、开合策略），按移动端交互改造（无 hover →
常显箭头 + 点按展开 + 大触控区）。

不处理：移动端与 hub 的直连（仍是 fixture 驱动，本次不动数据通路）；
移动端 Markdown 渲染器、输入区、顶栏、附件、会话列表等本次不涉及的部分；
PC 端已确认的交互规格（hover 显形等）—— 移动端按触屏惯例另定。

## 4. 裁决

- **共享而非复制（默认裁决）**：派生逻辑抽到 `packages/ui-thread`，两端共用。
  理由：PC 端这批逻辑被重写两次、两次都出过 bug（正则多一个裸 `|`、剥参数
  剥过头），复制一份等于把同一类 bug 变成两份维护成本。`WORKSPACE_MATRIX`
  要求包间只向下依赖，新增包只依赖 `@x3code/contracts`，矩阵随包登记（修宪法）。
- **文案注入而非引 copy（默认裁决）**：`@/strings` 是各 app 的路径别名，
  共享包引不到。共享包接收 `ToolCopy` 结构化文案表，PC 与移动端各自
  从自己的 strings 适配。这样中英文表仍是各端唯一真相。
- **模型适配而非改移动端领域模型（默认裁决）**：移动端 `ChatMessage` 是
  fixture 模型，不具备 `editHunks`/`path`。本轮**扩充实领域模型**（加
  `toolName`/`argsPreview`/`output`/`exitCode`/`editHunks`/`subagents`
  可选字段），而不是把它改成 PC 的 `ToolCallModel`——移动端的渲染分层
  （turns/fold/group）依赖 `ChatMessage` 的大量既有语义（status 行、失败通知、
  生成中指示器），整体换模型会连带推翻与本次无关的部分。
- **状态词表统一（单一真相推论）**：`ToolCallStatus` 住 contracts；移动端
  `MessageRunStatus`（running/success/error）退役，`ChatMessage.status`
  直接用 `ToolCallStatus`。执行行状态前缀要的就是这套词表，两套并存等于
  每个调用点挂一个映射适配器。
- **图标语义共享、图标组件各端映射（发现三）**：`toolIconKey` 下沉；
  PC 映射 lucide-react、移动端映射 lucide-react-native（组件不同源，
  语义只能有一套）。
- **开合策略共享（发现三）**：`autoOpenForGroup`/`autoOpenForCall`/`callExpandable`
  下沉——「失败必须可见」是产品裁决，两端各写一遍就会漂移。移动端「展开」
  的形态是底部 Sheet（见下条），失败可见由行内「运行失败」整句 + 红色承担，
  不自动弹 Sheet（自动弹层在触屏上是打断，不是可见性）。
- **触屏交互（用户裁决）**：移动端无 hover，所有原本 hover 显形的箭头
  **常显**；展开一律点按，触控区不小于 44px（iOS HIG）。
- **文件级 diff 在移动端同样合并（用户裁决「与 PC 一致」）**：同一文件多次
  编辑合成一个 diff，展开走底部 Sheet（移动端不做行内展开——屏幕窄、
  代码块需要横向空间）。diff 入口行与执行行同形态（铅笔 + 「已编辑」+ 文件名）。
- **移动端 tool 消息字段定案**：tool 消息的执行语义走
  `toolName`/`argsPreview`/`exitCode`/`editHunks`/`subagents`；执行输出走
  正文 `text`（与 user/assistant 同一个正文字段，不另设 `output`——同一事实
  不设两个字段），行内不展示、只进详情 Sheet。`title` 退给 code 工件、
  `summary` 退给 status 信封，tool 消息不再使用旧的「动作名 + 描述」文案对
  （旧 fixture 的叙述性 title/summary 随旧实现一起退役）。

## 5. 实施顺序

- M1 共享包 `packages/ui-thread`：契约（contracts 补 `ToolCallStatus`）+
  纯派生函数 + 单测（从 PC 现有测试迁移，断言行为不迁实现）。
- M2 PC 端接线改为消费共享包，删除 PC 侧重复实现（原
  `tool-summary.ts` / `tool-group-summary.ts` / `tool-row-label.ts` /
  `hunk-lines.ts` / `edit-file-groups.ts` / `file-object-name.ts` /
  `tool-kind.ts` / `call-detail.ts` / `tool-row-icon.ts` / `tool-group-icon.ts`
  归并为 `tool-icons.ts`），PC 行为零变化（四门全绿 + 覆盖率不降为验收）。
- M3 移动端领域模型扩字段（状态词表统一）+ strings 文案补齐（ToolCopy 表 +
  diff/详情 Sheet 文案）。
- M4 移动端聊天页重写：tool-group（并行批次聚合 + 常显箭头 + 自动开合）、
  tool-row（类别图标 + 状态前缀 + 命令摘要 + 失败退出码尾）、thinking-row
  （收起预览 + 点按展开）、process-fold（轮级开合策略 + 变更摘要）、
  file-diff（入口行 + 底部 Sheet 展示合并后 diff）、tool-detail-sheet
  （完整命令 + 输出 + 退出码/耗时）。
- M5 删除旧实现（旧组件、旧字段、旧 fixture 文案对）、跑移动端 jest + 四门、
  覆盖率不降、走查（bw 驱动真实浏览器打开 web 导出产物，DOM 断言 + 截图）。

每步独立可回滚。M2 与 M1 是一组（不拆开提交——拆开即双轨）；M3-M5 是移动端
聊天页的一次原子换代（拆开即新旧双轨渲染），合成一个提交。

## 6. 测试口径

- 共享包：直接从 PC 现有用例迁移（tool-summary 忠实展示/注释剔除/空白折平、
  tool-group-summary 四档文案与命令保底、tool-row-label 失败成句、
  hunk-lines 分隔、groupEditsByFile 归并、call-detail 开合策略、
  图标语义键），断言只写行为不写实现。
- PC 回归：M2 后四门全绿、覆盖率不降、`bun test` 数量不减
  （基线：2404 pass / 313 文件；覆盖率 funcs 85.12 / lines 92.69）。
- 移动端：既有 jest 全部重跑（基线：24 suites / 137 tests；
  覆盖率 stmt 96.62 / branch 89.07 / func 96.64 / line 98.42）；新增
  - 并行批次聚合成组头（文案与 PC 同源：编辑了文件运行了命令）
  - 单条执行不套组头，行 = 状态前缀 + 命令摘要
  - 箭头常显（触屏无 hover，收起态也有箭头）
  - 失败行「运行失败」整句 + 退出码尾
  - 同文件多次编辑合成一个 diff 入口，Sheet 内红绿行对照
  - 组头/执行行/思考三者的触控区（≥44px）与顺序
  - 自动开合：运行中/失败常开，正常完成收起；手动意图优先
