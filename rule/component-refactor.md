# 组件重构方法论：从不合理的 props 面到区域自组装

> 本文档回答一个问题：**当一个组件的 props 面或状态架构已经不合理，怎么判、怎么拆、为什么这么拆。**
> 它与《组件拆分规范》（rule/component-split.md）正交互补：那篇管「一个文件装几个组件」的粒度问题，
> 本篇管「一个区域的 props/状态架构」的结构问题（漏斗、搬运、状态枢纽）。粒度问题先查那篇；
> 出现本篇 §1 的症状时，用本篇的方法论立项。
> 实证全部来自本仓 T32（侧栏 store 订阅化，2026-09）：一个 34-props 组件归零的全过程。
> 候选应用对象：`ThreadStage`（god-object `workspace` prop）、`Composer`（约 40 props）、
> `SettingsScreen`（spread 面）、`useLiveWorkspace` 溶解。

## 1. 判定依据：什么算「不合理的组件」

不要凭「props 多」立项——props 数量是症状不是病因。逐条对照下面的信号清单，
**命中 ≥3 条，或命中任一硬信号（S4/S5），才立项**。每条都给出可操作的判别法与 T32 实证。

### 症状清单

| # | 信号 | 判别法 | T32 实证 |
| --- | --- | --- | --- |
| S1 | **回调搬运费** | 回调 props 的函数体只是调用一个「到处可得」的稳定引用（store 动作/单例/控制器方法）。数转发链长度：同一组回调在 ≥2 层组件逐字转发 | SessionRow 5 个回调 × Pinned/Project/平铺 3 条转发链（D1） |
| S2 | **memo 防守注释** | 同一文件 ≥2 处注释在解释「引用恒定/不被击穿/防重挂」。注释密度是代码在自认：父级重渲是常态，靠手工纪律防守 | workspace-main 三处（:105/:292/:320），其中一处是 T30 审查高-2 的修补 |
| S3 | **状态提升强迫** | 某状态的真实消费者分布在 ≥2 个不相邻区域（含非 UI 消费者：热键、Esc 链、标题栏），于是提升到共同祖先 → 祖先 props 面膨胀成枢纽 | sidebarCollapsed/searchOpen 被 Esc 链+热键+TitleBar 消费，全部挤在 WorkspaceMain |
| S4 | **漏斗架构**（硬信号） | 全应用只有一个组件订阅数据源，其余全靠 props 分发。判别：`useStore`/selector 的消费点数量 = 1。细粒度订阅设计在第一层就被终止 | 唯一订阅点是 useLiveWorkspace，聚合 20 个 selector 成大对象交给 WorkspaceMain |
| S5 | **多套状态容器并存**（硬信号） | 模块级可变对象 / 手搓 effect 同步 / useState / 真 store，≥3 种生命周期语义并存。手搓容器是差版 store：无订阅、无批处理、有补写窗口 | uiState 模块可变对象 + 8 个 useState + zustand store 三轨（B6） |
| S6 | **一事多轨** | 同一事实有两条产出路径：文案（label props vs 直读 copy）、类型（双定义）、实例（同一工厂两处创建） | filterEmptyLabel props vs copy.sidebar 直读（B7）；createWorkspaceActions 双实例 |
| S7 | **死物与腐烂** | noop 交互钮、描述已删功能的孤儿注释、测试夹具残留字段。测试目录在 typecheck 豁免面（tsconfig exclude `__test__`）时腐烂不可见 | 工作流/插件市场 noop 钮（B3）、onOpenRuntime 孤儿注释（B4）、三处夹具残留（B5/B8/B9） |
| S8 | **重渲半径超标** | 高频更新源（tick、流式批推、轮询）挂在树的高处，重渲半径覆盖全树。判别：更新源的组件位置到真正消费 DOM 的距离 | ages 30s tick 在 WorkspaceMain，每 tick 全树重渲且必然击穿子 memo（B2） |

### 判定表

- 命中 S4 或 S5 → 直接立项（结构性缺陷，不会自愈）。
- S1+S2 同时命中 → 立项（搬运费+防守成本已经是持续税）。
- 其余组合 ≥3 条 → 立项。
- 只命中 S1 或只命中 props 数量多 → **不立项**，先查《组件拆分规范》是不是粒度问题，或只是补几个 useMemo 的事。

## 2. 拆分依据：三条裁决线（为什么这么拆）

拆分不是把 props 分组收进对象——那只是把症状打包。所有裁决都从三条线推出：

### 裁决线一：状态归属——按「写权 + 生命周期」拆 store，不按「谁读」拆

**读是自由的，写是受限的。** store 是模块单例，import 即订阅，任何组件一行 `useStore(store, s => s.x)`
就能拿到数据——「很多地方要用」从来不是问题（问题是数据被独家订阅后改走了 props 通道）。
决定状态住哪里的只有两个维度：

| 维度 | live 类 store | ui 类 store |
| --- | --- | --- |
| 写者 | 只有事件折叠层（协议/服务端真相镜像） | 任何区域的交互动作 |
| 生命周期 | 跟随数据源（重连/挂死即 reset） | 跟随应用（跨重挂载存活） |

为什么必须至少两类、不能一个大 store：**reset 语义会互相污染**。T32 的具体形态：
live store 在宿主挂死时 `reset()` 清空全部会话镜像——若草稿、侧栏几何也在同一 store，
宿主重启会把用户没发出去的草稿一起清掉。写权混装必然导致生命周期互相绑架。
反过来也不要拆更多：没有第三种写权/生命周期组合时，多一个 store 只多一份仪式。

**推论（状态提升的解药）**：跨区消费者的状态不是提升到共同祖先，而是**下沉到 store**——
S3 的热键/Esc 链/标题栏改为直接订阅或 `getState()` 读取，枢纽组件失去存在理由。

### 裁决线二：数据形态——折叠进 store，派生不进 store，交互态进 ui store

| 形态 | 归宿 | 判别 | 实证 |
| --- | --- | --- | --- |
| **折叠**（事件→状态的一次性换算，成本高、写时算一次） | store 动作 | 读取方若各自折叠会产生不一致镜像 | threads 的事件折叠（fold-events） |
| **派生**（读取时的形状变换，纯计算） | 纯函数 + 按输入引用缓存（WeakMap），定义在领域模块，import 即用 | 进 store 就是第二真相源 | sessionCardsOf（先例 threadModelOf） |
| **交互态**（「应用此刻在干什么」而非「服务端是什么」） | ui store | 整页开合、几何、草稿、面板目标 | ui-store 全部字段 |

派生的引用缓存是 memo 纪律的根治：无关 set 不产出新引用，下游 memo 天然不被击穿——
S2 的手工防守注释可以整体删除。

### 裁决线三：行为通路——命令走单例，副作用居留订阅点

- **命令单例**（`workspaceActions` 型）：调用时读 store 真相 + invoke 桥。工厂保留导出作为换装缝，
  生产装配 `export const x = createX()`。S1 的搬运费在这里整体消失——组件 import 即调，零 props。
- **编排单例**（`navigation` 型）：跨区域意图（「选会话 = 先退整页」）无参化，全部输入来自 store 与
  命令单例。出口唯一，新增入口零成本。
- **副作用居留**：store 动作零 IO；需要副作用的动作（开页即拉数据）放在**订阅点的 effect**
  （由开合态订阅驱动），或独立控制器模块（异步装配 + 竞态防护）。
  违反它 = store 里混进 invoke，测试面崩塌。

### 边界一句话（目标态的组件契约）

> **数据与区域自态走 store（谁用谁订阅）；跨区意图走 store 的开合字段与编排单例；
> 展示组件只收自己的渲染数据。**

## 3. 目标形态：区域自组装四层

```
壳（Shell）            0 props。几何/让位逻辑；React.memo 挡住父级无关重渲
├─ 区域（Region）      0–3 props。自订阅（live/ui store）→ 调派生纯函数 → 组装子组件；
│                      高频更新源（tick/轮询）收敛在最小区域内部
│   ├─ 展示（Presentational）  ≤7 个数据 props、零回调 props；SSR 可测；
│   │                          行内动作直调单例（可选回调契约 = 死灵活性，删）
│   └─ …
└─ 单例动作层          命令/编排/控制器模块；组件 import 即调
```

各层判据：

- **壳**：改名后名字是「一个区域」（侧栏/线程舞台/输入区），不是「一个功能」。
  0 props 时 memo 边界结构性可靠——不存在不稳定 props。
- **区域**：订阅面 = 恰好它的 DOM 消费的字段（细到 Set.has(key)/布尔）。
  一个区域的重渲半径 = 它订阅的字段集合，写在重渲边界回归用例里钉死。
- **展示**：props 全部是「这一行/这一块自己的数据」（session/age/active），出现回调 props
  就问一句「它调的是不是单例」——是就删掉回调。
- **单例**：无状态或只持有模块级注入缝（`installXxx` 可变值注入，AGENTS.md 认可）。

## 4. 怎么拆：五步操作流程

### Step 1 审计（动代码之前，产出三清单）

逐文件过四条标准（正确性/契约符合/实现质量/依赖方向），产出：

- **B# 真 bug 清单**：编号 + 位置 + 级别 + 处置（本波修/挂账）——重构同时清创，不许「先记着以后修」。
- **D# 重复清单**：转发链、双轨实现，各附提取计划。
- **C# 契约缺口**：要改的公共接口与消费方清单（grep 验证，不许凭感觉）。

纪律：没读过的文件不许标已审计；测试目录在 typecheck 豁免面时要专门目检夹具腐烂。

### Step 2 逐模块裁决表

每个旧文件一行：**复制 / 复制+微修 / 重构 / 重写 / 不移植**，附审计依据编号。
- 复制的前提是审计无可挑剔；发现问题就升级裁决，并把问题带进新实现的测试计划。
- 「重写」的模块先产出**同构**版本（每个行为分支/错误路径/副作用在新代码有可指认的对应物），
  优化放后续独立动作——否则「重写」会悄悄变成「顺手重新设计」，等价性失去锚点。
- **零双轨**：旧路径（被取代的 hook/类型/可变对象）与新模式不得共存——删除发生在引入新模式的
  **同一个提交**内（T32 实例：uiState 与 SidebarProps 都在其替代者落地的提交内删除）。

### Step 3 里程碑正序（依赖不倒置）

固定三段式，顺序不可换：

1. **M1 状态层**：store 落地 + 命令/编排单例 + 全部状态迁移 + 旧容器同提交删除。
   组件 props 面**此步不变**（数据源换了，喂数方式没换）——失败域最小，行为零变化。
2. **M2 区域化**：壳归零 props、区域订阅化、展示组件收窄、死物清理、重渲边界回归用例。
3. **M3 编排收尾**：全局链（Esc/热键/标题栏）接 store、注册表化、最终瘦身。

自检：**下一里程碑所需的一切状态与动作，必须在上一里程碑就位**（T32 定稿审查抓到过
M2 依赖 M3 字段的倒置，重排后才可实施）。每步独立提交可 revert；提交信息引用任务文档节号。

### Step 4 每步三门验证

1. **四门**：lint 0-0 / typecheck / build / test 全绿。
2. **行为保全清单对照**：开工前把旧行为写成编号规格（热键门控矩阵、Esc 收起序、
   可见性折算、重挂载存活语义……），每步逐条对照。**语义变更不允许静默发生**——
   要么保全，要么以「用户裁决/有意变更」落档并带反向断言。
3. **独立对抗审查**：独立会话（子 agent）只喂 diff + 旧实现 + 规格基线，指令
   「假设新代码与旧实现行为不一致，找出偏差」。审查者不实现、实现者不自审。
   偏差清单逐条处置后才提交。

### Step 5 收口核销

- **假绿抽查**（独立会话）：对照测试迁移矩阵，矩阵之外的删除/跳过/断言弱化 = 核销无效。
  T32 实证：抽查抓出「矩阵声明的去处落空」与「7 类症状钉子删除未声明」——全绿不等于保真。
- **覆盖率只升不降**：与基线（worktree 实测）对比逐列报告，禁止调阈值；新增面的低覆盖文件
  用深度交互测试拉平（T32 实证：补绑定层/行交互测试把 Lines 拉回并反超）。
- 任务文档验收清单打勾、状态推「已核销」、实施记录逐波留档（含审查发现与处置）。

## 5. 测试策略（按层分形态）

| 层 | 测试形态 | 装置 |
| --- | --- | --- |
| 纯函数（派生/裁决/视图模型/纯状态机） | 单测直调，表驱动钉词表封闭性与序 | 无 |
| 展示组件 | SSR 冒烟（renderToStaticMarkup）锁 DOM 形态与症状钉子 | 无 DOM |
| 区域/壳/交互 | 客户端渲染：模块 store `setState` 种子 → 断言 DOM 与 store 双向 | happy-dom + createRoot + act |
| 重渲边界 | Profiler 数提交 + 渲染探针（非 memo）数父级传导；无关 set 必须零提交、订阅 set 必须到达 | 同上 + 假定时器 |
| 控制器 | 注入缝换装可控异步源，断竞态代次与复位 | 无 DOM |

**装置适配记录制度**：环境的每一条限制必须落档并给替代覆盖，不许静默绕过。T32 实测坑清单：

1. happy-dom 的 GlobalRegistrator 把 `window` 落成 globalThis 本体——给 window 写「别名」
   会覆盖全局实现并递归自身（挂载死锁）；同体时天然无需别名。
2. React 19 受控 input 的合成 `input` 事件链在 happy-dom 不通（click/keydown 正常）：
   「输入→store」方向用 store 种子 + 受控回显单侧覆盖，真实键盘路径挂账 e2e。
3. 同一 act 批内 down+move 不刷新 ref（批处理），事件序列要拆 act。
4. Profiler 的 children 元素与 onRender 必须**稳定引用**，否则 Profiler 自身随父级提交（假阳性）。
5. 测试内定义组件违反 `ui/no-multi-component`（嵌套定义禁令同样约束测试）——宿主组件提模块级。

## 6. 拿走即用的检查表

### 立项前自检（§1 判定表过一遍后）
